## Project Scope — read this first

The project's scope narrowed significantly. Large parts of this document describe systems that are
**deprecated and frozen**: they may still have code in the repo, but they are not in scope, their
tables may no longer exist in the database, and they should not be extended or "fixed" unless
explicitly asked.

**In scope (active development):**
- **Organization group visits** — orgs request visits, admins/PDs review and approve, volunteers
  sign up for slots, waitlist, staffing minimums, completion. Tables: `visits`,
  `visit_registrations`, `visit_notes`.
- **Program Directors (PDs) and regions** — regional ownership of orgs, volunteers and visits.
  Tables: `pd_regions`, `pd_region_places`, `users.assigned_region_id`, `visits.assigned_pd_id`.
- **Compliance documents** — VSC (volunteer) and vaccine records (dogs), with an admin/PD
  review-and-verify flow. Tables: `document_verifications`, verification columns on `users`/`dogs`.
- **Admin & PD dashboards** — group visits, manage volunteers, manage orgs, user requests.
- **Organization dashboard** — browse and register for visits, manage own visits and profile.
- **Transactional email** (Resend + Handlebars templates) for visit lifecycle events.
- **Capacitor native app** shell.

**Deprecated and frozen (do not extend):**
- **The availability system** — weekly templates, recurring RRule slot generation, the custom time
  picker. The `appointment_availability` table **no longer exists**; `appointments.availability_id`
  is a vestigial column with no foreign key.
- **Individual ↔ volunteer matching** — browsing dogs, audience-category matching, 1:1 visit
  requests. Tables `appointments`, `chat_requests`, `individual_audience_tags`,
  `volunteer_audience_preferences` persist but are out of scope.
- **The entire chat feature** — Stream Chat, connection management, chat logs, admin chat
  monitoring, and the unread-message email notification system that depends on it. Tables
  `appointment_chats`, `chat_logs`, `message_read_status`, `pending_email_notifications`.
- **Push notifications** (`device_tokens`) — built, not in active scope.

### Database reference

`docs/DB_SNAPSHOT_DEV.md` is the **current-state** schema reference, generated by introspecting
DevDB (columns, constraints, indexes, RLS policies, triggers). Consult it rather than reconstructing
state from the migration history.

`docs/ORGANIZATION_VISITS_SCHEMA.md` is the append-only **migration history**. Its prose table specs
have drifted from reality in places (e.g. it lists `visits.special_needs_notes`, which was renamed to
`event_description` by Migration 34). Where the two disagree, the snapshot wins.

There is no migration runner — migrations are hand-run SQL files in `scripts/`. A file being present
and untracked in git does not mean it is unapplied; check the snapshot.

> **Assume scripts in `scripts/` are stale** unless verified. Several reference dropped tables or
> functions that do not exist in DevDB (e.g. `update_get_nearby_dogs_function.sql` creates
> `get_nearby_dogs_with_availability`, which is not in the database).

### Email Notification System *(DEPRECATED — chat-dependent)*

> This describes unread-*chat*-message notifications. Visit lifecycle emails are active and are a
> separate path (`src/app/utils/mailer.ts` + `templates/emails/`).

- **Smart Batching**: Look-ahead batching consolidates all pending notifications per user into one email
- **Delayed Delivery**: 1-hour delay (configurable via `EMAIL_NOTIFICATION_DELAY_HOURS` in `utils/notificationConfig.ts`)
- **Unread Verification**: Checks Stream Chat API before sending to avoid emails for already-read messages
- **Automatic Cancellation**: Notifications canceled if user reads message before delivery
- **Appointment Context**: Emails include appointment date/time, dog name, sender name, and message preview
- **Cron Schedule**: Runs every 30 minutes via Vercel Cron (configurable in `vercel.json`)
- **Database Tracking**: `pending_email_notifications` table tracks scheduled, sent, and canceled notifications
- **Webhook Integration**: Notifications created automatically when messages arrive via Stream Chat webhook

### User Archive System
- **Purpose**: Allows admins to archive stagnant/inactive accounts without permanent deletion
- **Archive Process**:
  - Admin clicks "Archive User" button in Manage Users interface (Individual or Volunteer tabs)
  - System checks for active appointments (pending or confirmed status)
  - If appointments exist, modal shows warning with breakdown of confirmed vs pending
  - Admin can cancel or proceed with archiving
  - If confirmed, all active appointments are canceled automatically
  - Cancellation emails sent to other parties with reason: "Canceled by Sunshine Administrator"
  - Pending email notifications are canceled
  - Active chats are closed
  - For volunteers, associated dog is also archived
  - User status set to 'archived', `archived_at` timestamp recorded
- **Archived User Experience**:
  - Cannot log into dashboard (shows "Account Archived" message with contact info)
  - Hidden from all search results (RLS policies filter by `status='approved'`)
  - Cannot create or confirm appointments (API validation checks)
  - Existing appointment history preserved (not deleted)
- **Unarchive Process**:
  - Admin navigates to "Archived Users" tab
  - Clicks "Unarchive" button next to user
  - User status restored to 'approved', `archived_at` set to NULL
  - For volunteers, dog status also restored to 'approved'
  - User can immediately access platform again
- **Implementation**:
  - Database: `archived_at` timestamp column in `users` table
  - API: `/api/admin/archive-user`, `/api/admin/unarchive-user`, `/api/admin/archived-users`
  - Frontend: [AdminManageUsers.tsx](src/components/admin/AdminManageUsers.tsx) with new "Archived Users" tab
  - Dashboard: [dashboard/page.tsx](src/app/(pages)/dashboard/page.tsx) intercepts archived status
  - Migration: `scripts/addArchivedStatus.sql`

## Development Patterns

### Database Operations
- Always use appropriate Supabase client:
  - `createSupabaseServerClient()` for server-side with RLS
  - `createSupabaseAdminClient()` for admin operations bypassing RLS
  - `useSupabaseClient()` for client-side operations
- RLS policies are comprehensive - check `docs/DATABASE_SCHEMA.md` for policy details

### Stream Chat Integration *(deprecated)*
- Use `StreamChatClientManager` for connection management
- Token caching prevents unnecessary API calls
- Always handle disconnection callbacks in React components
- Use `isClientReady()` checks before channel operations

### PD Scoping (important)

PD visibility is **not** enforced by RLS. The only PD-relevant policy is "Admins and PDs can view
all visits" — scoping happens client-side.

- **Visits** are filtered in the client on `v.assigned_pd_id === currentUserId`
  (`src/components/admin/AdminVisits.tsx`).
- **`visits.assigned_pd_id` is a denormalized snapshot**, resolved once at visit creation from the
  org's region owner (`src/app/api/visits/route.ts`). Nothing recomputes it afterwards except
  `POST /api/admin/assign-org-region` with `cascade_visits`, which fires only when an *org* changes
  region. Changing a *region's* owner PD does not update existing visits.
- **Volunteers and orgs** are filtered on `users.assigned_region_id`, with the region filter
  defaulting to the PD's own region.

When seeding or fixing data, the chain must be built in order: `pd_regions.owner_pd_id` →
`pd_region_places` → `users.assigned_region_id` → `visits.assigned_pd_id`.

## Security & Privacy

### Row Level Security
- RLS protects the core tables (`users`, `dogs`, `visits`, `visit_registrations`, `visit_notes`,
  `document_verifications`, `pd_regions`) with correctly scoped policies
- **Known gap:** several peripheral tables carry policies *named* for a privileged role but written
  with `roles=public` and a `true` predicate, which ORs away the restrictive policies on the same
  table — affects `role_change_audit`, `welcome_messages`, `chat_logs`, `appointment_chats`,
  `volunteer_audience_preferences`. See `docs/DB_SNAPSHOT_DEV.md` for the exact policy text.
  Fix before onboarding real users; not a blocker for internal testing
- PD scoping is **not** enforced by RLS — see "PD Scoping" above
- Users can only see approved users and their own data
- Admin operations use service role key to bypass RLS when needed
- Chat data protected with user-specific access policies

### Authentication Security
- Clerk handles secure authentication flow
- JWT tokens used for Supabase integration
- Stream Chat tokens server-generated with user validation

### Data Protection
- Personal information visible only to authorized users
- Chat messages logged for admin monitoring but protected by RLS
- Email addresses and contact info secured at database level
- Location data used only for matching, not exposed publicly

## Claude Code Communication Guidelines

### Problem-Solving Approach
- **Be skeptical and honest**: Avoid claiming to "see the problem" or guaranteeing fixes when making assumptions or guesses
- **Acknowledge uncertainty**: Be explicit when inferring vs. verifying information from code
- **Avoid overconfident language**: Don't use phrases like "This will fix the issue" unless you can verify the solution
- **State what you can actually confirm**: Differentiate between what you can observe in the code vs. what you're hypothesizing
- **Ask clarifying questions**: When uncertain, ask for more information rather than making assumptions

### Troubleshooting Best Practices
- Test changes when possible rather than assuming they work
- Acknowledge when you're working with incomplete information
- Be direct about limitations in understanding complex interactions (especially mobile browser behaviors, iOS Safari, etc.)
- Focus on observable facts from code inspection rather than speculation
